# Вход и синхронизация через Supabase

В репозитории подготовлены вход, регистрация по email/паролю и синхронизация
снимка сотрудников (все месяцы, планы, фактические продажи и KPI). Серверный
проект пока не создан; `cloud-config.js` содержит пустые настройки. До подключения
приложение продолжает сохранять данные в браузере. Нельзя считать облачный вход
работающим до выполнения шагов ниже и проверки на настоящем проекте.

## Подключение

1. Создайте проект в Supabase под своим аккаунтом. Сохраните пароль базы данных
   у себя: приложению он не нужен.
2. Откройте SQL Editor проекта и выполните весь [schema.sql](../supabase/schema.sql).
   Создадутся таблица `salary_snapshots`, политики Row Level Security и функция
   `save_salary_snapshot` для записи с проверкой версии. Скрипт можно запускать
   повторно; существующие записи он не удаляет.
3. В Authentication → Providers проверьте, что включён Email. Оставьте подтверждение
   email включённым. В Authentication → URL Configuration укажите фактический
   адрес опубликованного калькулятора как Site URL. Он используется в письмах
   подтверждения. Пароль вводится только в форму входа и отправляется в Supabase
   через HTTPS, приложение его не сохраняет.
4. В Project Settings возьмите Project URL и публичный Publishable key
   (`sb_publishable_…`; также поддержан старый ключ `anon`). Запишите их в
   `cloud-config.js`:

   ```js
   window.SALARY_CLOUD_CONFIG = Object.freeze({
     url: 'https://YOUR_PROJECT.supabase.co',
     publishableKey: 'YOUR_PUBLIC_PUBLISHABLE_KEY'
   });
   ```

   Это публичные настройки для браузера. Ключи `service_role`, `sb_secret_…`,
   пароль базы данных и почтового сервера сюда помещать нельзя. Доступ к строкам
   ограничивают политики базы, а не скрытие публичного ключа.
5. Опубликуйте изменённый файл вместе с приложением. Внешних JS-библиотек,
   сборки и отдельного сервера приложению не требуется. На своей статической
   площадке разрешите HTTPS-запросы к домену своего проекта, если используете CSP.

Если email-провайдер Supabase ограничивает отправку писем, настройте SMTP в
самом проекте. Секреты SMTP не нужны в коде калькулятора.

## Использование

Зарегистрируйтесь, подтвердите адрес из письма, затем войдите с email и паролем.
Новые аккаунты открывают отдельный список сотрудников. Нажмите «Перенести
данные этого браузера», чтобы добавить существующие локальные данные в аккаунт.
Перенос сохраняет существующие записи аккаунта, копирует сотрудников с новыми
ID и не удаляет оригинал в локальном режиме. Повторное нажатие копирует их снова.

На другом устройстве откройте тот же калькулятор и войдите в тот же аккаунт.
Данные синхронизируются после правок, при возвращении сети, при фокусе окна и
каждые 30 секунд. Кнопка «Синхронизировать» запускает проверку сразу.
При выходе открывается локальный режим; кэш и резервные копии аккаунта остаются
в отдельном пространстве этого браузера и не показываются другому аккаунту.
Сессия хранится на устройстве для автоматического входа; выход завершает сессию
только этого устройства.

При одновременной правке на двух устройствах приложение не объединяет снимки
автоматически. Оно предлагает загрузить облачную версию либо отправить версию
этого устройства. Перед заменой локальных данных сохраняется резервная копия.
Для дополнительной копии перед выбором можно использовать существующий экспорт
JSON. Это синхронизация личного аккаунта, без совместного редактирования аккаунтов,
ролей руководителя и общего доступа между разными email.

## Проверки

Без облака выполняются обычные проверки расчётов:

```sh
node tests/calculator.test.cjs
node tests/realistic-plan.test.cjs
```

Для браузерного контракта запустите HTTP-сервер из корня репозитория, затем тест
в окружении с Python Playwright и Chromium по пути `/usr/bin/chromium`:

```sh
python3 -m http.server 8000 --bind 127.0.0.1
# В другом терминале:
python3 tests/cloud-sync.browser.py
```

Этот тест использует подменённый Supabase HTTP API. Проверяются регистрация,
два независимых устройства, перенос локальных данных, офлайн-правки, конфликт,
восстановление сессии и разделение аккаунтов. Настоящая отправка писем и
авторизация сервиса этим тестом не проверяются.

SQL отдельно проверяется в PostgreSQL через PGlite с тестовой реализацией
`auth.uid()` (без обращения к Supabase):

```sh
npm install --prefix /tmp/salary-db-check --cache /tmp/salary-npm-cache --no-audit --no-fund @electric-sql/pglite@0.3.14
PGLITE_MODULE=/tmp/salary-db-check/node_modules/@electric-sql/pglite/dist/index.js node tests/cloud-rls.test.mjs
```

Проверяются повторный запуск схемы, запрет анонимного доступа, изоляция записей
двух пользователей, отказ записи при старой версии и неверном формате данных.
PGlite нужен только для этой проверки и не добавляет зависимостей приложению.

После подключения реального проекта необходимо дополнительно проверить:
регистрация с письмом подтверждения, вход на двух устройствах, перенос данных,
правка на одном устройстве и загрузка на другом, выход/повторный вход,
восстановление доступа к API после обновления токена. Встроенный восстановитель
пароля пока не добавлен; пользовательский запрос сброса пароля — отдельная доработка.
